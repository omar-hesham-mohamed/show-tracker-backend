# Social Show Tracker — Architecture & MVP Plan

## Context

Build a social TV/movie tracking app: log what you've watched or want to watch, follow friends and see a feed of their recent watch activity, and maintain a self-reported daily watch streak (explicitly honor-system — no Netflix/streaming API verification, since that's not realistically available and isn't worth the complexity, similar to how Duolingo streaks work despite being trivially cheatable).

This replaces a free app that used to do this and has since shut down. Greenfield project, no existing code. Backend in Node (the user has professional experience in both Node and Spring/Java) — this plan leans on NestJS specifically because its module/controller/service/DI/decorator structure closely mirrors Spring Boot, which should make the learning curve much shallower than bare Express.

Target: a public, open-signup app — **mobile (iOS/Android) and web** — backed by a Node/NestJS API, using TMDB for show/episode metadata. Mobile and web share a single React Native/Expo codebase (via Expo's web target, `react-native-web`), not separate frontends.

**Status: finalized — ready for scaffolding (milestone 1).**

## Tech Stack

- **Backend**: NestJS + TypeScript (Express adapter). Chosen over bare Express because its DI/module/decorator conventions map ~1:1 onto Spring Boot concepts (`@Controller`≈`@RestController`, `@Injectable`≈`@Service`, Guards≈Spring Security filters/`@PreAuthorize`, Exception filters≈`@ControllerAdvice`). Gives a solo dev a consistent answer to "how do I structure this" without reinventing routing/DI/validation conventions from scratch.
- **ORM**: Prisma + PostgreSQL. Preferred over TypeORM despite TypeORM's more JPA-like decorator syntax, because Prisma's migration story (`prisma migrate dev` generates clean, reviewable SQL — closer to Flyway/Liquibase) and generated types are lower-risk for a solo dev. `$queryRaw` remains available as an escape hatch for hand-tuned queries (e.g. the feed).
- **Database**: PostgreSQL — relational fits the follow-graph + feed-join access patterns much better than a document store.
- **Mobile + Web**: React Native via **Expo (managed workflow)** + EAS Build/EAS Update for iOS/Android, and Expo's **web target** (`react-native-web`) for the browser build from the same codebase — **confirmed, not a separate frontend framework/stack**. Avoids maintaining two frontends (two component libraries, two auth/storage layers, two sets of bugs) at the cost of needing to audit each screen for a wider/desktop layout, since RN styling defaults assume a phone-sized viewport. Modern Expo (prebuild/config plugins) no longer requires "ejecting" to add native modules, and EAS Update gives OTA JS fixes without app-store review.
- **Show/episode data**: TMDB API, proxied through the backend (never call TMDB directly from the client — this is also the caching control point). TMDB also provides watch-provider (streaming availability) data.
- **API shape**: REST, not GraphQL — matches Spring/MVC familiarity, Nest's REST tooling (incl. `@nestjs/swagger` for free OpenAPI docs) is more mature than its GraphQL module, and the screen set is small/known enough that hand-designed endpoints avoid over/under-fetching without adding a second query paradigm to learn.
- **Repo layout**: simple two-folder repo (`backend/`, `mobile/`), no Nx/Turborepo — **unchanged by adding web**, since mobile and web are the same Expo codebase/project, not separate projects. Not worth the extra tooling investment for a solo project at this stage.

## Core Data Model (Prisma schema, `backend/prisma/schema.prisma`)

- **User**: `id, username (unique), email (unique), passwordHash, displayName, avatarUrl, bio, timezone (IANA string), isPrivate, currentStreakCount, longestStreakCount, lastStreakDate (date), deletedAt (nullable), createdAt, updatedAt`. `deletedAt` (soft-delete marker, indexed) is already in the schema ahead of the Phase 8 polish milestone — login and `JwtStrategy` both already exclude/reject soft-deleted users — but the actual `DELETE /users/me` scrub/anonymize flow isn't built yet (no `users` module exists).
- **RefreshToken** (as-built, not previously listed here): `id, userId (FK), tokenHash (unique), expiresAt, revokedAt (nullable), createdAt`. Stores only a SHA-256 hash of the opaque refresh token, never the raw value — see rotation/reuse-detection logic in the Phase 2 decisions below.
- **Follow**: `followerId, followeeId, createdAt` (composite PK; index both directions). **One-way follow model** (like Letterboxd/Twitter), not mutual friend-requests — matches "open public sign-up," needs no pending/accepted state machine. `isPrivate` on User gates a locked profile; a `FollowRequest` table can be added later if approval-gated private accounts are wanted post-MVP. **Confirmed.**
- **Block** (as-built, not previously listed here): `blockerId, blockedId, createdAt` (composite PK, indexed both directions) — schema already scaffolded for the Moderation endpoints (`endpoints.md` §Moderation); blocking's effect on existing Follow edges is application-layer logic, not yet built as a service/controller.
- **Show** (TMDB cache): `id, tmdbId, mediaType (movie|tv), title, overview, posterPath, backdropPath, releaseDate, tmdbRating, genres (jsonb), status, seasonCount (TV only, null for movies), lastSyncedAt, watchProviders (jsonb, nullable), watchProvidersSyncedAt (nullable)`. **Correction to this doc's original model**: `tmdbId` is unique only in combination with `mediaType` (`@@unique([tmdbId, mediaType])`), never on its own — TMDB movie IDs and TV IDs are independent sequences, so an unrelated movie and TV show can legitimately share the same numeric ID. Watch-provider data has its own `watchProvidersSyncedAt` clock, tracked independently from `lastSyncedAt` (metadata) — both currently use the same 7-day TTL constant, but as separate fields so they can diverge later.
- **Episode**: `id, showId (FK), seasonNumber, episodeNumber, name, airDate, overview, stillPath, lastSyncedAt` — unique on `(showId, seasonNumber, episodeNumber)`.
  - Local caching is required (not optional) because watch-log rows need a local FK target, feed/list queries need to SQL-join against show data, and it insulates the app from TMDB downtime/rate limits. Cache-aside: fetch + upsert on first miss, or on read when `lastSyncedAt` is past TTL (lazy, on-read refresh — no scheduled/background job). **TTL: 7 days for both metadata and watch-provider/availability data** (see Phase 3 decisions below). Well within TMDB's ToS ceiling of 6 months max local caching.
- **WatchLogEntry**: `id, userId (FK), showId (FK), episodeId (FK, nullable), status (WATCHED|WATCHING|WANT_TO_WATCH), rating (nullable), watchedAt, note (nullable), createdAt, updatedAt`. Index `(userId, status)` and `(userId, watchedAt desc)`. No uniqueness constraint on `(userId, showId)` — rewatches are allowed as separate rows. **Rating scale: 0.5–5.0 in 0.5 increments** — stored as `Decimal(2,1)` (as-built in `schema.prisma`, not `Int`/half-point-integer as originally considered — chosen to avoid binary float rounding on a value rendered back exactly), validated server-side to reject anything off the 0.5 grid.
- **Streak**: denormalized counters on `User` (`currentStreakCount`, `longestStreakCount`, `lastStreakDate`), updated on write (not derived live on every read):
  - On a WATCHED log for "today" (user's local date): same day → no-op, consecutive day → increment, gap → reset to 1.
  - **Timezone handling**: client sends its local date (`YYYY-MM-DD`) with the log; server validates it's within a sane window of server time (loose check — honor-system by design, just block obviously spoofed future dates). Avoids classic midnight/DST off-by-one-day streak bugs. `watchedAt` stays the durable source of truth so a reconciliation script can recompute streaks if the counter logic ever drifts.
- **Feed**: query-time join for MVP, not fan-out-on-write — get followee IDs from `Follow`, then `WatchLogEntry WHERE userId IN (...)` ordered by recency, joined to `Show`, cursor-paginated. Revisit with fan-out (or hybrid pull/push) only if a real user has a large follower count or measured feed latency becomes a problem.
- **DeviceToken** / **NotificationPreference** (Phase 8 polish — schema pre-built, not previously listed here): `DeviceToken(id, userId (FK), expoPushToken (unique), platform (ios|android), createdAt)`; `NotificationPreference(userId (PK/FK), streakReminders, newFollowerAlerts, activityAlerts, updatedAt)`. Already present in `schema.prisma` even though no notifications module/endpoints exist yet — the full data model was designed up front rather than added piecemeal at Phase 8.

Deliberately deferred post-MVP: likes/comments on watch entries, region-keyed watch-provider cache, OAuth login, private-profile follow requests, search-by-person/filmography resolution (no `Person` model or profile screen exists — `person` results from TMDB search are filtered out entirely for MVP rather than resolved into a filmography), **server-derived streak-day determination** (see below).

- **Streak-day hardening (deferred, not MVP)**: MVP trusts the client-supplied `watchedAt` date for the streak-day decision (loose future-date validation only, honor-system by design — see Streak decisions above). A stronger version, worth doing post-MVP rather than at launch: since `User.timezone` (IANA string) is already captured at signup, compute "today" **server-side** from request-arrival time converted into the user's stored timezone, and only let a log whose `watchedAt` matches that server-computed local day affect `currentStreakCount`/`longestStreakCount`. `watchedAt` would stay client-suppliable for backdating diary entries (a real feature, not just a streak input) — it would just stop being trusted as the source of truth for *today's* streak decision specifically, closing the trivial "spoof today's date to fake a streak" hole without losing the ability to log a past watch. Not done at MVP because the honor-system streak is an accepted, deliberate simplicity trade-off (see Context — "similar to how Duolingo streaks work despite being trivially cheatable"); revisit if streak-gaming turns out to matter in practice.

## Backend Bootstrap & Global Conventions (as-built, `src/main.ts` / `src/app.module.ts`)

- **Global prefix**: every route is served under `/api/v1` except `health` (`app.setGlobalPrefix('api/v1', { exclude: ['health'] })`) — matches `endpoints.md`'s base-path convention.
- **Global `ValidationPipe`**: `whitelist: true` (strips unknown properties), `forbidNonWhitelisted: true` (400s instead of silently dropping unexpected fields), `transform: true` (query/body values get coerced to their DTO's declared type, e.g. `page` string → number). Its `exceptionFactory` is the actual source of the `400` + `details: string[]` shape documented in `endpoints.md`'s Errors convention — that shape isn't hand-built per endpoint.
- **Global error filter**: `HttpExceptionFilter` (`src/common/filters/http-exception.filter.ts`), registered via `APP_FILTER`, catches *every* thrown error — including non-`HttpException` runtime errors, mapped to a bare 500 — and normalizes it to `{ statusCode, error, message, path }`, filling `error` from Node's `http.STATUS_CODES` table when the exception didn't supply one, and passing through any extra fields (like `details`) from the exception's response body untouched.
- **Global guard**: `JwtAuthGuard` (`src/common/guards/jwt-auth.guard.ts`), registered via `APP_GUARD` — secure-by-default; `@Public()` skips auth entirely, `@OptionalAuth()` attempts auth but falls back to an anonymous (`null`) request instead of a 401 on a missing/invalid token. A raw JWT-library error (e.g. `JsonWebTokenError`) is caught and rethrown as a clean `UnauthorizedException` instead of leaking through to the global filter's 500 branch.
- **Rate limiting is opt-in per route today, not global** — `ThrottlerModule.forRoot(...)` registers the module/config, but no `APP_GUARD` wires `ThrottlerGuard` globally. `/auth/signup` and `/auth/login` apply it explicitly via `@UseGuards(ThrottlerGuard)` + `@Throttle(...)` (5 requests/60s). Any new write endpoint needs the same decorator pair added by hand until Phase 8's general write-endpoint throttling lands.
- **CORS** (as-built): `app.enableCors({ origin: allowedOrigins })` in `main.ts`, where `allowedOrigins` is parsed from the comma-separated `ALLOWED_ORIGINS` env var — an explicit allowlist, not a wildcard, since the API is not purely public-anonymous. No `credentials: true` is set, since web auth uses header-based Bearer tokens rather than cookies (see the Web-app decisions below), so no cross-origin cookie/credential mode is needed.
- **Health check** (`GET /health`, public, excluded from the `/api/v1` prefix): pings `SELECT 1` via Prisma. On success: `200 { status: 'ok', db: 'ok', uptimeSeconds }`. On DB failure: **`503`** (via `ServiceUnavailableException`, not a `200` with `db: 'error'`), same body shape, passed through the global filter.

- **A few tests intentionally assert current, known-buggy behavior** (marked inline `[KNOWN ISSUE]`/`[FOUND VIA TESTING]`) rather than masking it — they function as regression trackers for bugs found through this testing pass, not as endorsements. One documented this way is still open: `HttpExceptionFilter` loses the message on a raw `new HttpException(string, code)` (not reachable from any current throw site in this codebase, which only uses the built-in subclasses — see `http-exception.filter.spec.ts`). The other bug this pass found (`timezone: "UTC"` being rejected) has already been fixed — see the Phase 2 signup-validation bullet below — and its test now asserts the corrected behavior instead.
- The Milestone 9 login-timing side-channel (`AuthService.login` skipping `bcrypt.compare` for unknown users) is also captured as an executable test in `auth.service.spec.ts`, not just prose — it currently asserts the vulnerable behavior (`bcrypt.compare` not called), and should be flipped to `toHaveBeenCalled()` once that fix lands.
- **Bug found via Phase 4 live verification, already fixed — stale generated Prisma Client**: the manual end-to-end walkthrough for Phase 4 (real Postgres + real TMDB) hit `500`s on *every* endpoint touching `Show` — including pre-existing Phase 3 routes like `GET /shows/tv/:tmdbId`, not just the new watch-log code. Root cause: `node_modules/@prisma/client` (the generated client) was stale — it still referenced a `Show.recommendations` column that exists in neither the current `schema.prisma` nor the database (`prisma migrate status` reported the migrations themselves as up to date; only the generated client was out of sync), so every query touching `Show` failed with Prisma error `P2022`. `HttpExceptionFilter` doesn't log the underlying exception on an unhandled 500 (see above), so the real error only surfaced by querying Prisma directly outside Nest. Fixed by running `npx prisma generate`; on Windows this first requires stopping the running dev server, since it holds a file-lock on the compiled query-engine `.dll` that `prisma generate` needs to overwrite (`EPERM` otherwise). **Takeaway**: `npx prisma generate` isn't automatic — run it any time `schema.prisma` changes (or after a fresh clone/pull) and the generated client might be behind it, and expect to stop `nest start --watch` first on Windows before doing so.
- **Bug found writing the new watch-log DTO specs, already fixed — `IsDateString({ strict: true })` doesn't reject timestamps**: `create-watch-log.dto.ts`/`update-watch-log.dto.ts`'s `watchedAt` field used `@IsDateString({ strict: true })`, on the (wrong) assumption that `strict` restricts the accepted format to date-only (`YYYY-MM-DD`). Tracing into `validator.js`'s `isISO8601` (what `class-validator`'s `IsDateString` delegates to): `strict` only gates an *additional* real-calendar-date check (e.g. rejects `2026-02-30`) — it does nothing to the format itself, so a full timestamp like `2026-08-07T00:00:00.000Z` passed validation. That would have gone on to corrupt `watch-log.service.ts`'s `` new Date(`${dto.watchedAt}T00:00:00.000Z`) `` construction (a timestamp already containing its own `T...Z` suffix, with another one appended). Caught by a spec (`create-watch-log.dto.spec.ts`) written specifically to assert the documented contract ("only a date-only string is accepted") rather than just the happy path. **Fix**: added `@Matches(/^\d{4}-\d{2}-\d{2}$/)` alongside the existing `@IsDateString({ strict: true })` on both DTOs — the regex enforces the date-only shape, `IsDateString`'s `strict` still catches invalid calendar dates within that shape.
- **Bug found writing the new watch-log DTO specs, already fixed — latent `Reflect.getMetadata is not a function` gap**: `create-watch-log.dto.spec.ts` and `list-watch-log.dto.spec.ts` (the two DTOs using `class-transformer`'s `@Type(() => Number)`) crashed at import time when run as their own isolated Jest module graph — `@Type()` needs the `reflect-metadata` polyfill loaded onto the global `Reflect` object first, and every *previously* -passing spec file happened to pull that in transitively via a `@nestjs/common`/`@nestjs/core` import, so this was never triggered before. `src/tmdb/dto/search-shows.dto.ts` uses the same `@Type(() => Number)` pattern and has never had a dedicated spec — so this was a pre-existing, latent gap, not something introduced by the new DTOs. **Fix**: added `"setupFiles": ["reflect-metadata"]` to both Jest configs (`package.json`'s unit-test config and `test/jest-e2e.json`) rather than patching individual spec files — makes this robust for any future spec on any `@Type()`-using DTO, including `search-shows.dto.ts` if it ever gets one.

## Adversarial Code Review — Phases 1–4 Audit (2026-08-19)

Explicit "try to break it" pass across all of Phases 1–4 (auth, TMDB, watch-log, common infra), requested separately from normal feature development — same spirit as the Milestone 9 adversarial-testing plan below, done early against the current surface rather than waiting until pre-launch. Ran as a multi-angle finder + independent verification pass; every finding below was additionally spot-checked by hand against the actual source (not just trusted from the automated pass) before being logged here. 10 real findings, ranked by severity. **The 5 critical findings (500s / wrong status codes from routine bad input or infra blips, not exotic attacks) are fixed, each with a regression test proving it. The 5 medium/low findings are deferred — logged here so they don't need rediscovering, not forgotten.**

### Fixed

1. **`PATCH /watch-log/:id` with an explicit `null` field crashed the request with a raw 500** (`update-watch-log.dto.ts`, `watch-log.service.ts`). `class-validator`'s `@IsOptional()` treats `null` the same as `undefined` and skips the rest of that field's validators — so `{"status": null}` sailed past `@IsEnum` and reached a `NOT NULL` Postgres column, which Prisma surfaces as an unhandled `P2011`, not an `HttpException`. **Fix**: replaced `@IsOptional()` with `@ValidateIf((_, value) => value !== undefined)` on every field in `UpdateWatchLogDto` — omission (`undefined`) still skips validation, but an explicit `null` now runs through (and fails) the field's own validator. Uniform across all four fields for a simple contract ("PATCH doesn't accept null, only omission means don't change this"), even though `rating`'s column is nullable and wouldn't itself have crashed. **Tests**: `update-watch-log.dto.spec.ts` (explicit-null rejection per field), `watch-log.e2e-spec.ts` (`PATCH` with `{"status": null}` → `400` over real HTTP).
2. **A malformed pagination cursor crashed `GET /watch-log/me` instead of 400ing** (`watch-log.service.ts`). `decodeCursor` (`cursor.util.ts`) only checks that cursor fields are strings, never that `watchedAt` parses as a real date — a cursor encoding `{"watchedAt":"not-a-date",...}` produced an `Invalid Date`, which Prisma can't serialize into a `WHERE` clause and throws a raw, unhandled error for. **Fix**: added `Number.isNaN(watchedAtDate.getTime())` check right after constructing the date in `findMine()`, throwing `BadRequestException('Invalid cursor')` — kept in the service (not `cursor.util.ts`) since the codec is meant to stay generic/reusable for future callers that may not have a `watchedAt` field at all. **Tests**: `watch-log.service.spec.ts`, `watch-log.e2e-spec.ts`.
3. **Concurrent signups for the same email/username could 500 instead of 409** (`auth.service.ts`). Classic check-then-act race: `signup()` does a `findFirst` duplicate check, then `create()`, with no transaction and no handling for the DB's own unique-constraint violation. Two near-simultaneous signups for the same email both pass the check; the second one's `create()` throws a raw `PrismaClientKnownRequestError` (`P2002`), not an `HttpException`. **Fix**: wrapped `create()` in a try/catch, translating `P2002` into the same `ConflictException` the non-concurrent path already throws (using `error.meta.target` to pick the email-vs-username message). Anything else rethrows unchanged. **Tests**: `auth.service.spec.ts` (constructs a real `Prisma.PrismaClientKnownRequestError`), `auth.e2e-spec.ts` (fires two real concurrent signups via `Promise.allSettled`, asserts exactly one `201`/one `409`, never a `500`).
4. **A DB failure during authentication was reported to the client as a `401` with the raw internal error message leaked** (`jwt-auth.guard.ts`). `JwtStrategy.validate()` has no try/catch around its `prisma.user.findUnique` call; per `passport-jwt`'s own source (`self.fail()` for a bad/expired JWT, `self.error()` only for the verify callback's own thrown errors), the guard's `err` parameter is populated *exclusively* by `validate()` throwing — either its own deliberate `UnauthorizedException()` (unknown/deleted user, safe) or an unexpected error such as a DB failure (not safe). The old code unconditionally re-wrapped any truthy `err` as `UnauthorizedException(err.message)`, mislabeling infra failures as 401s and leaking their message. **Fix**: rethrow `err` unchanged instead of re-wrapping it — an `HttpException` (our own deliberate one) passes through exactly as intended; anything else correctly falls to the global filter's generic, non-leaking 500. (Wraps a non-`Error` rejection reason in a real `Error` first, to satisfy throwing-a-proper-error hygiene — not expected in practice, since `validate()` only ever throws real `Error`/`HttpException` instances.) **Tests**: `jwt-auth.guard.spec.ts` (two pre-existing tests that asserted the old leaking behavior were rewritten to assert the fix; one new test confirms a deliberate `UnauthorizedException` still passes through cleanly).
5. **`HttpExceptionFilter` never logged unhandled (non-`HttpException`) errors — every 500 above was invisible in logs**. This is exactly how the stale-Prisma-client bug (above) stayed hidden long enough to require bypassing Nest entirely to diagnose. **Fix**: added a `Logger` to the filter, logging `exception.stack` (or `String(exception)` for a non-`Error` throw) whenever the exception isn't an `HttpException` — expected 4xx/​normal-flow exceptions stay silent, matching the logging discipline `TmdbService` already established. **Tests**: `http-exception.filter.spec.ts` (logs for unhandled exceptions, stays silent for normal `HttpException`s; every other test in the file now silences `Logger.prototype.error` by default so its own deliberate-500 tests don't spam real log output).

### Deferred (not fixed this pass — logged for later)

6. **`GET /shows/search` has no error handling**, unlike every other TMDB-calling method in `tmdb.service.ts` (`getShowDetail`/`getWatchProviders`/`getRecommendations`/`getSeasonDetail` all wrap their TMDB call, log on failure, and degrade to 502/stale-cache/404). A TMDB timeout or 5xx during search — the most-hit discovery endpoint — currently produces an unlogged 500 instead of the same clean handling. Fix shape: same try/catch + logging pattern as the other four methods.
7. **`getShowDetail`/`getSeasonDetail` mislabel a DB failure during the post-fetch `upsert` as "TMDB is currently unavailable."** The `try` block wraps both the TMDB call and the subsequent Prisma write; any error during the write falls into the same catch, gets logged and reported as a 502 TMDB outage even when TMDB responded fine — actively hiding real DB problems from monitoring. Fix shape: narrow the `try` to just the TMDB call; handle the upsert's own errors separately.
8. **`AuthService.refresh()`'s revoke-then-issue isn't transactional.** The old refresh token is revoked and the new one created as two separate awaited Prisma calls; a crash/DB blip between them permanently strands that session (dead old token, no new one, no recovery path except full re-login). Fix shape: `prisma.$transaction([...])` around both.
9. **`watch-log.service.ts`'s `update()`/`remove()` rely entirely on the prior `findOwnedOrThrow()` ownership check** — the mutation queries themselves (`update({where:{id}})`, `delete({where:{id}})`) carry no `userId` filter as a defense-in-depth backstop. Not currently exploitable (today's code always checks first), but a future method that forgot to check first would have nothing else stopping it. Fix shape: add `userId` into the mutation's own `where` clause too.
10. **`seasonCount` overcounts shows with a Specials season** (`tmdb.mapper.ts`, `mapTvDetail`): `raw.seasons?.length ?? 0` counts every entry TMDB returns, including `season_number: 0` (Specials), which most shows with bonus content have. An 8-season show with specials reports `seasonCount: 9`. Fix shape: `raw.seasons?.filter(s => s.season_number > 0).length ?? 0`.

## App Structure (Mobile + Web)

Same screens, same navigation structure, same codebase — built once via Expo/React Navigation and rendered on both targets. Web-specific work is layout/responsiveness, not new screens.

- **Auth stack**: Welcome → Sign Up / Log In → onboarding (username, timezone capture).
- **Main tabs**: Home/Feed, Discover/Search, My List/Library, Profile.

## MVP Build Phasing (sequential milestones)

Web is built **in parallel with mobile from Milestone 1 onward** (not a later/separate phase) — every milestone below targets both outputs from the same Expo codebase.

1. **Scaffolding** — NestJS backend (modules, Prisma + Postgres via Docker, env config, health-check endpoint); Expo app shell with placeholder screens and React Navigation wired up, **web target enabled** (`expo start --web` / web build working) alongside iOS/Android from day one.
2. **Auth** — email+password signup/login, JWT access+refresh tokens, username/timezone capture at onboarding. Defer social login (Apple/Google) until closer to app-store submission.
3. **TMDB integration** — `TmdbService` proxy/cache-aside client; search + show-detail + season/episode endpoints, upserting into the local `Show`/`Episode` cache. *(Riskiest early milestone — movie vs TV data shapes differ, season/episode nesting is nontrivial, and watch-provider data is region-gated with attribution requirements.)*
4. **Personal watch log** — log status/rating, personal list + diary screens. This alone is already a usable single-player app and a good soft-launch checkpoint.
5. **Streaks** — write-time increment logic per the timezone-safe design above, with unit tests around the date-boundary edge cases specifically.
6. **Follow graph** — follow/unfollow, followers/following lists, public profiles, privacy toggle.
7. **Social feed** — query-time join endpoint with cursor pagination, feed UI. *(Also risky — easy to get subtly wrong under time pressure: missing indexes, N+1 show-loading per feed item, offset-vs-cursor pagination bugs.)*
8. **Polish** — push notifications (streak reminders, new follower/activity), avatar upload (`POST /users/me/avatar`), rate limiting/abuse guardrails on write endpoints, account deletion (`DELETE /users/me` — cascade/anonymize — worth designing into the schema now rather than retrofitting).

   **Users-endpoint ownership, clarified**: `endpoints.md`'s Users section maps across phases as follows — `POST /users/me/avatar` and `DELETE /users/me` → Phase 8 (above); `GET /users/:username` (public profile) → Phase 6, implicitly, via "public profiles". **`GET /users/me` and `PATCH /users/me` (the logged-in user's own profile read/update) are the only two Users endpoints not assigned to any phase** — no `users` module exists yet at all. Worth building alongside Phase 6 (public profiles need the same module/patterns) rather than leaving it to surface as a surprise gap later.
9. **Pre-launch hardening — adversarial testing, load testing, deploy readiness.** Comes after the app is feature-complete (post-Polish), before Shipping stage 1 (backend deploy). Explicit task for whoever/whatever is helping build this (including Claude, when asked): actively try to break the app, not just review the code — this is a distinct pass from normal development.
   - **Adversarial/security testing** (authorized, against your own local/staging instance): attempt auth bypass (tampered/expired JWTs, replayed/reused refresh tokens outside the documented rotation-theft path, hitting guarded routes with no token); IDOR (fetch/modify another user's `WatchLogEntry`, private profile data, or blocked-user data by guessing IDs); rate-limit bypass on `/auth/login` and `/auth/signup`; oversized/malformed payloads against `ValidationPipe` (confirm `whitelist`/`forbidNonWhitelisted` actually reject what they should, not just happy-path bodies); mass-assignment attempts (extra fields in a request body that shouldn't be settable, e.g. trying to set someone else's `userId` or `isPrivate` via an unrelated endpoint); rating/streak grid validation bypass (off-grid ratings, spoofed-future `watchedAt`, rapid-fire streak manipulation); privacy-gating bypass (reading a private profile's data or a blocked user's content through an endpoint that forgot the check); enumeration via error-message differences (e.g. does login's "invalid credentials" message or timing leak whether an email exists).
   - **Known issue to fix here, not a hypothetical**: `AuthService.login` (`auth.service.ts`) short-circuits on `!user || !(await bcrypt.compare(...))` — when the account doesn't exist, `bcrypt.compare` (a deliberately slow, ~100ms hash) is skipped entirely, so a request for a nonexistent user returns measurably faster than one for a real user with a wrong password. That timing gap lets an attacker enumerate valid emails/usernames by measuring response time alone, without needing the 409 signup message or any other UI hint. Fix: always run `bcrypt.compare` against a fixed dummy hash when `user` is null, so both branches pay the same cost and return in comparable time — cheap to add, no reason to defer it past this milestone.
   - **Concurrency/race-condition testing**: concurrent requests hitting the same streak counters or the same refresh token (double-submit/refresh races — does the "reuse revokes everything" logic behave correctly or over-trigger under legitimate concurrent retries, per the known tradeoff already logged above); concurrent writes to the same `WatchLogEntry`.
   - **Load/stress testing**: realistic-scale concurrent load against the feed endpoint (query-time join — this is the one already flagged as riskiest for perf) and TMDB-proxy endpoints (confirm cache-aside actually prevents a thundering herd of duplicate TMDB calls under concurrent cache-miss requests for the same show); confirm behavior under Postgres connection-pool exhaustion and under TMDB's own rate limits (does a TMDB 429 degrade gracefully via the existing stale-fallback path, or crash the request).
   - **Deploy-readiness checklist**: all `.env` secrets rotated from placeholder/dev values (`JWT_ACCESS_SECRET` especially — never ship the `.env.example` default); `ALLOWED_ORIGINS` locked to real production domains only, no leftover `localhost`; `npm audit` clean (or triaged); confirm `HttpExceptionFilter` never leaks stack traces/internal error detail in production responses; `prisma migrate deploy` dry-run against a prod-like database; structured logging/error monitoring wired up (e.g. Sentry) so failures post-launch are visible, not silent; confirm every write endpoint has rate limiting, not just `/auth/*` (per the Phase 8 goal); HTTPS enforced end-to-end on both the API host and web deploy; DB backup/restore plan exists before real user data accumulates.
   - **`app.set('trust proxy', 1)` (as-built, `main.ts`)**: without this, Express's `req.ip` resolves to the reverse proxy's own IP on Railway/Render rather than the real client's, and `ThrottlerGuard` (`auth.module.ts`) keys its rate limit on `req.ip` — so in production, `/auth/login`/`/auth/signup`'s 5-requests/60s limit would silently collapse into one shared bucket for every user behind the proxy instead of limiting each client individually. Set now rather than left for a deploy-day surprise, since it has no effect locally (no proxy in front of dev) and only matters once actually deployed.
   - **`app.enableShutdownHooks()` (as-built, `main.ts`)**: NestJS's `OnModuleDestroy` lifecycle (which `PrismaService` uses to `$disconnect()`, `prisma.service.ts`) only fires on an explicit programmatic `app.close()` unless this is called — it does **not** fire automatically on a process signal. Every Railway/Render redeploy sends the old container a `SIGTERM` before killing it; without shutdown hooks enabled, that DB connection would never close cleanly, relying on the process dying to release it instead of a graceful disconnect.

## Cross-Cutting Gotchas To Keep In Mind

- Never embed the TMDB API key client-side — always proxy through the backend.
- Rating scale is 0.5–5.0 in half-star increments (confirmed) — build the star-picker UI and rating column with half-point granularity from the start; retrofitting later is painful once data and UI assume a scale.
- Baseline moderation even at MVP: block-user, private-profile toggle, write-endpoint rate limiting.
- **CORS**: the backend must allow the web app's origin (native mobile requests don't send an `Origin` header or trigger preflight, so this wasn't a concern before web existed) — configure this in Milestone 1 scaffolding, not as an afterthought when web auth breaks mysteriously.
- **Token storage differs by platform**: `expo-secure-store` (native Keychain/Keystore) isn't available on web — needs a small storage abstraction that falls back to `localStorage`/`sessionStorage` on the web target. See the auth decision below for the security tradeoff this implies.
- **Responsive layout**: RN component styling defaults assume a phone-sized viewport. Audit each screen (especially Feed, Show Detail, My List) for a sane wide/desktop layout rather than assuming phone styles look acceptable stretched across a browser window.
- **Regenerate the Prisma Client after any `schema.prisma` change** (`npx prisma generate`) — it is not run automatically, and a stale generated client fails at query time (`P2022`, missing/extra column) rather than at build time, so `npm run build`/`tsc` won't catch it. On Windows, stop the running dev server first (`nest start --watch` locks the compiled query-engine `.dll`, causing `EPERM` on generate) — see the Phase 4 Testing bullet above for the bug this actually caused.

## Scale & Shipping

- **Design target**: ~1,000–10,000 users. Not a hard ceiling, but the honest range for a solo-dev soft launch — the current architecture (single Postgres instance, query-time feed joins, no fan-out, no Nx monorepo) comfortably handles this with no changes. Deferred scaling techniques (fan-out feeds, read replicas, CDN-fronted images, caching layers) are known upgrade paths to reach for later once real usage data shows an actual bottleneck — not worth designing for now.
- **Backend hosting**: Railway or Render — both give Postgres + a Node deploy from a git push with minimal ops work, cheap/free tiers that fit this scale, and an easy upgrade path later. Leaning Railway for slightly simpler Postgres+app bundling, but this isn't a consequential lock-in.
- **Web hosting**: static export of the Expo web build, deployed to Vercel or Netlify — separate deploy target from EAS Build/Submit (mobile app-store path), but same CI trigger point. Not a consequential lock-in choice; revisit only if SSR needs emerge.
- **Shipping stages**:
  0. Milestone 9 (pre-launch hardening — adversarial + load testing, deploy-readiness checklist above) completed first, against a local/staging instance, before any deploy.
  1. Backend deployed to Railway/Render.
  2. Soft launch: EAS Build to TestFlight (iOS) and Google Play internal/closed testing (Android), **plus** the web build deployed to Vercel/Netlify, once milestones 1–5 (auth, TMDB, watch log, streaks) are solid — gets it onto real phones and a real URL without a public listing or app-review gate.
  3. Public release via EAS Submit (mobile) and removing any access-gating on the web deploy, only after the social layer is done and the soft launch has validated the core loop feels good.

## Decisions Log

- One-way follow model — confirmed.
- Rating scale: 0.5–5.0, half-star increments — confirmed.
- Core stack (NestJS, Prisma, Postgres, Expo, Railway/Render) — confirmed as-is, no swaps.
- **Phase 2 (Auth) design — confirmed:**
  - Password hashing: **bcrypt** (not argon2id — familiarity with Spring's `BCryptPasswordEncoder` weighed over argon2id's marginally better GPU resistance; fine at MVP scale).
  - Token lifetimes: **15 min access / 30 day refresh**.
  - Refresh token rotation: reuse of an already-rotated/revoked token (theft signal) **revokes all sessions** for that user, not just the reused token.
    - **Known tradeoff, accepted as-is for now**: this is standard theft-detection (matches OAuth2/Auth0 practice), but the blast radius is aggressive — a false positive (e.g. two tabs or a retried request racing to redeem the same refresh token concurrently) looks identical to theft and logs the user out of every device. No grace window for near-simultaneous reuse is implemented. Revisit with a short grace window if this causes real user-facing lockouts; not worth the added complexity pre-emptively for a casual social app's threat model.
  - Rate limiting: `@nestjs/throttler` added on `/auth/login` and `/auth/signup` **now**, ahead of the general write-endpoint rate limiting still deferred to Phase 8 polish.
  - JWT: HS256, single shared secret (no RS256 — single backend, nothing else verifies tokens).
  - Guards: global `JwtAuthGuard` via `APP_GUARD` (secure-by-default), with `@Public()` and `@OptionalAuth()` decorators to opt out per-route.
  - Access-token validation is DB-backed (loads the user via Prisma each request, rejects if `deletedAt` is set) rather than pure stateless signature checking — trades a DB read per request for immediate lockout on deletion/ban.
  - Username uniqueness is case-insensitive (lowercase-normalized for the check); `displayName` stays free-form for casing; emails stored lowercased.
  - **Logout** revokes only the presented refresh token (i.e. only that device/session) — other logged-in devices are unaffected. The access token itself is **not** blacklisted on logout; it simply keeps working until its own 15-minute expiry. Building true instant access-token revocation would mean checking a blacklist on every request, defeating the point of a stateless access token — accepted trade-off given the short TTL.
  - **Refresh token storage**: only a hash (`tokenHash`) is stored, never the raw token, so a DB leak alone doesn't yield usable tokens. Hashing algorithm can be a fast hash (SHA-256), not bcrypt/argon2id — unlike passwords, refresh tokens are already high-entropy random values with nothing guessable to brute-force, so slow/salted password-hashing is unnecessary here.
  - **Refresh token cleanup**: no automatic pruning of expired/revoked `RefreshToken` rows in Phase 2 — harmless at MVP scale (thousands of rows, trivial for Postgres). A periodic cleanup job (`@nestjs/schedule`, delete where `expiresAt < now()` or long-revoked) is deferred to the Phase 8 polish milestone.
  - **Signup field validation (as-built, not previously documented)**: `username` — regex `^[a-z0-9_]{3,20}$` (case-insensitive match, stored lowercased), 3–20 chars, letters/digits/underscore only; `password` — 8–72 chars (72 is bcrypt's own input-length ceiling, enforced explicitly rather than silently truncating longer input); `displayName` — 1–50 chars; `timezone` — resolved via `Intl.DateTimeFormat('en-US', { timeZone: value }).resolvedOptions().timeZone` rather than checking membership in `Intl.supportedValuesOf('timeZone')`: that canonical-names-only list excludes real, resolvable aliases like `"UTC"` and the whole `Etc/*` namespace, which the resolver itself correctly accepts (found via unit testing — `is-iana-timezone.validator.spec.ts` — the original `supportedValuesOf`-based check rejected `timezone: "UTC"` outright, a value real clients commonly send). Input is also normalized to its canonical form (`@Transform` in `is-iana-timezone.validator.ts`) before validation/storage, so `"africa/cairo"` or `"US/Eastern"` are accepted and stored as `"Africa/Cairo"`/`"America/New_York"` rather than rejected for casing/aliasing that doesn't change the actual zone — only genuinely unresolvable input (`"Not/AZone"`, offset notation like `"+02:00"`, whitespace-padded input) is rejected.
  - **Env vars (as-built)**: `.env.example` currently defines `DATABASE_URL`, `PORT`, `JWT_ACCESS_SECRET`, `TMDB_ACCESS_TOKEN` — no `JWT_REFRESH_SECRET` exists because refresh tokens are opaque `crypto.randomBytes(32)` values (hashed with SHA-256 for storage), not JWTs, so there's nothing to sign.
- **Phase 3 (TMDB Integration) design — confirmed:**
  - **`tmdbId` is the public-facing show identifier** throughout the client-facing API (search results, `GET /shows/:tmdbId` path param, `POST /watch-log` request body) — the internal `id` (UUID) exists only for DB FK relations and only appears embedded in response objects once a `Show` row has actually been cached.
  - **Search routes to a different TMDB endpoint per `type`**: `type=movie` → `/search/movie` directly, `type=tv` → `/search/tv` directly, `type=all` (default) → `/search/multi` + client-side filter (TMDB has no server-side `media_type` filter on `/search/multi`, and it can also return `collection` results, not just movie/tv/person — both `person` and `collection` are dropped, only `movie`/`tv` mapped/returned).
    - **Why not always call `/search/movie` + `/search/tv` and merge for `all` too**: `/search/multi` is the only way to get a single TMDB-side relevance ranking spanning movie+TV. Two independently-sorted lists have no shared, comparable score to merge/interleave correctly — inventing our own cross-type ranking would likely be worse than TMDB's, and would double the TMDB calls on the default (`all`) search path. Accepted cost: `/search/multi`'s `total_pages` count includes the `person`/`collection` entries we then drop, so an "all" page can come back with fewer than 20 items — a minor, acceptable imprecision versus the alternative.
  - **Search is never cached** — every `GET /shows/search` call hits TMDB live, unconditionally, including repeats of the identical query string. Cache-aside only applies to requests keyed on a bounded identifier (`tmdbId` for show-detail, `(tmdbId, seasonNumber)` for season-detail); a free-text search query is unbounded per-user input with near-zero cache-hit potential, so there's nothing worth caching there.
  - **Recommendations carousel (`GET /shows/:mediaType/:tmdbId/recommendations`) — same "never cached" reasoning as search, confirmed**: wraps TMDB's `/movie/{id}/recommendations` or `/tv/{id}/recommendations` and returns the raw-ish list live on every call, using the same lightweight `ShowSearchResultDto` shape as search results (no separate `Show.recommendations` cache column, no TTL). A recommendation list is exactly the same shape of problem as search — a low-cache-value list of stubs — so it gets the same treatment. The only thing that gets persisted from a recommendations response is a specific show once the user actually taps into it, which reuses the *existing* `getShowDetail` cache-aside path unchanged — recommendations don't introduce a new caching mechanism, just a new list-producing read. No pagination (`cursor`/`page`) on this endpoint — it's a fixed-size shelf (TMDB's first page, ~20 items), not an infinite list. If TMDB returns an empty list (thin signal for obscure/new titles), the client is expected to hide the carousel rather than the API falling back to `/similar` — cosmetic edge case, not worth a second TMDB call/code path.
  - **Response cleaning/mapping** (`TmdbService`'s boundary layer, applies to every TMDB response before it touches the DB or the client): explicit allowlist of fields (never spread TMDB's raw response, which includes dozens of fields — budget, production companies, homepage, etc. — the schema has no use for); flatten `genres: [{id, name}]` → `string[]` of names; normalize TMDB's inconsistent nulls (`release_date` can be `""` for unreleased titles, not `null` — mapped to `null` explicitly, not left as an empty string that would produce an `Invalid Date`); `include_adult=false` on every search call. Validating the parsed shape (e.g. via Zod) before upserting is worth doing but not locked in as a hard requirement yet.
  - **Movie/TV field mapping**: TMDB models movies and TV as different shapes, not one shape with a type flag — `title`/`release_date`/`runtime` (movie) vs `name`/`first_air_date`/`episode_run_time` (TV). `TmdbService` normalizes both into the unified `Show` schema (`title`, `releaseDate`, `mediaType`) at the boundary; nothing downstream of that mapping ever sees TMDB's raw field-name divergence.
  - **Season/episode fetch: lazy per-season, not eager.** `GET /shows/:tmdbId` returns season *stubs* only (number + episode count — already free on TMDB's show-detail response); the full episode list for a season is fetched/cached only when that season is opened (`GET /shows/:tmdbId/seasons/:seasonNumber`), not upfront when the show is first cached.
    - **Why**: eagerly fetching every season on first view means N synchronous TMDB calls (one per season) for shows with many seasons (long-running procedurals/soaps/anime can have 500+ episodes) — either a slow first request or added complexity (background job/queue) to hide that. It also means storing hundreds of `Episode` rows for content most users will never scroll to, since most logging happens at the show or current-episode level, not by browsing full back catalogs. Lazy pays a one-time, cache-amortized round-trip only for seasons someone actually opens, matching the app's real access pattern better than eager does.
  - **Cache-aside is read-triggered, not scheduled**: a stale row (`lastSyncedAt` past TTL) only gets refreshed on the next request that hits it — that one request pays the TMDB round-trip latency synchronously (no stale-while-revalidate/background-refresh for MVP, kept simple at this scale; revisit only if this causes a real user-facing latency complaint).
    - **Future option, not built now**: stale-while-revalidate (always serve the cached copy immediately even if expired, refresh in the background for the next reader) would trade "occasionally the triggering request sees slightly-stale data" for "no request ever pays the TMDB round-trip synchronously." Worth revisiting if the synchronous-refresh latency spike ever becomes a real user-facing complaint — not worth the added complexity (background job/queue) pre-emptively.
  - **TMDB is free** for non-commercial use with required attribution (logo + "not endorsed or certified by TMDB" notice in an About/Credits section, per `endpoints.md`'s watch-provider note).
    - **Commercial-use limitation**: TMDB defines a use as commercial if its *primary purpose is to create revenue for the owner* — explicitly includes charging users a fee for the app, or selling an app that integrates TMDB content. That requires a separate paid **Commercial API Key**/written agreement (contact TMDB directly); the free/standard key does not permit it. Ads within an otherwise-free app are commonly stated (in TMDB's community forum, not the formal ToS text) to be fine under the standard key — treat that as a useful signal, not a guarantee, and re-verify with TMDB directly before shipping ads.
    - **Relevance here**: no monetization is currently planned, so the free non-commercial tier covers MVP as-is. This becomes a blocking dependency — not just a nice-to-know — the moment any paid tier, one-time purchase, or paywall is considered; get the commercial license sorted before building that, not after.
  - **Mapper/types split (as-built, not previously documented)**: `tmdb-api.types.ts` holds typed raw TMDB response shapes; `tmdb.mapper.ts` holds the pure translation functions (one per TMDB response type) into internal DTOs/Prisma-ready shapes described in the "Response cleaning/mapping" bullet above — `TmdbService` never touches a raw TMDB field name (`poster_path`, `first_air_date`, etc.) directly, only the mapped output.
  - **HTTP client config (as-built)**: `HttpModule.registerAsync` sets `baseURL: https://api.themoviedb.org/3`, a **5-second timeout**, and injects `Authorization: Bearer <TMDB_ACCESS_TOKEN>` — the **v4 Read Access Token**, not the v3 API key — on every request via `TmdbModule`. Individual calls in `TmdbService` never set auth or base URL themselves.
  - **Resilience on TMDB failure (as-built, a real behavior beyond what's described above)**: on any TMDB fetch error other than a 404, `getShowDetail` / `getWatchProviders` / `getSeasonDetail` all fall back to serving the existing cached/stale row (with a warning log) rather than failing the request outright, *if* a cached copy exists; only when there's no cache at all does the request fail with `502 Bad Gateway`. A TMDB `404` always throws a `404 NotFoundException` regardless of cache state (an unknown ID is unknown, not "stale"). This is a lighter-weight measure than the stale-while-revalidate option discussed below — it only serves stale data reactively, after a live refresh has already failed, rather than proactively serving-then-refreshing-in-background.
  - **`region` query param on watch-providers is currently a no-op**: `getWatchProviders` accepts it (per `endpoints.md`) but always fetches/caches `DEFAULT_WATCH_PROVIDER_REGION` (`'US'`) server-side regardless of what's passed — consistent with the "only the default region is ever fetched/cached" deferral above, but worth calling out explicitly since the request shape still advertises the param as if it changes behavior.
  - **Season freshness is keyed off the first cached episode's `lastSyncedAt`**, not a separate season-level timestamp — there is no `Season` table to store one on (see the `synthesizeSeasonMeta` doc comment in `tmdb.service.ts` for the full reasoning).
- **Web app added, built in parallel with mobile from Milestone 1 — confirmed:**
  - Same Expo/React Native codebase targets web via `react-native-web`, not a separate frontend framework — one codebase, one auth layer, one set of screens.
  - **Web auth reuses the existing header-based Bearer token flow** (no cookie-session addition for web) — same auth code path and same backend endpoints as mobile, no second auth mechanism to build/maintain.
    - **Known tradeoff, accepted as-is**: for a mobile app there was no meaningful alternative to header-based tokens (no browser cookie jar), but a browser *does* have a more XSS-resistant option (httpOnly cookies) that this choice forgoes for web. The access/refresh tokens on web must live in JS-accessible storage (`localStorage`/`sessionStorage`), which is exposed to theft via XSS in a way an httpOnly cookie wouldn't be. Accepted for now to avoid a second auth code path and CORS/CSRF-cookie complexity; revisit if the web app ever handles data sensitive enough to justify the added complexity, or if an XSS vector is found.
  - **CORS**: backend needs an allowed-origins config for the web app's domain(s), added at Milestone 1 scaffolding — not previously needed since mobile requests don't go through browser CORS.
- **Phase 4 (Personal Watch Log) design — confirmed:**
  - **Streak recompute is fully deferred to Phase 5**, not partially built here — `POST /watch-log` and `PATCH /watch-log/:id` omit `streakAfterWrite` from their responses entirely (endpoints.md updated with an inline note), and `User.currentStreakCount`/`longestStreakCount`/`lastStreakDate` are never touched by this module. Rationale: Phase 5 is a dedicated milestone with its own timezone-safe design and date-boundary test pass — building a naive increment now would just be thrown away.

  - **Show resolution reuses `TmdbService.getShowDetail(mediaType, tmdbId)` unchanged** (`src/tmdb/tmdb.service.ts`) rather than adding a second TMDB-fetch/cache-aside path — `POST /watch-log` is just another caller of the existing cache-aside, same as `ShowsController`.
  - **Cursor pagination**: a small shared codec (`src/common/pagination/cursor.util.ts`, `encodeCursor`/`decodeCursor`, base64url JSON, `BadRequestException` on malformed input) is factored out since endpoints.md scopes cursor pagination to multiple future list endpoints (feed, followers/following) as well as this one. Each service still builds its own keyset `WHERE` comparison — `WatchLogService` keys on `(watchedAt, id)` — since sort columns differ per resource; only the encode/decode step is shared.
  - **Rating grid validation** (`IsHalfStarRating`, `src/watch-log/dto/is-half-star-rating.validator.ts`) is a new custom `class-validator` decorator, same pattern as `IsIanaTimezone` — checks `rating * 2` is an integer in `[1, 10]`.
